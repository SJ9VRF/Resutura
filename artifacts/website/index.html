01 · Flagship project · Learning from Failure for Reliable Agents

Resutura

Effect-semantic recovery for computer-use agents: deciding whether to verify, repair, rewind, compensate, preserve, or stop after the world has already changed.

Measured mechanism result: in the bundled Chromium effect-semantics study, Resutura succeeds on committed misdirection and concurrent-change cases where Base / Retry / Verify / Rewind fail, while matching Verify on ambiguous commits and safe-aborting 100% of non-compensatable cases. 2 paired trials per method/scenario; deterministic planner; not a frontier-model benchmark.

60-second takeaway: Resutura is not another retry agent. It reasons about recovery after actions cross from reversible execution state into persistent shared-world effects, then chooses among verification, repair, rewind, compensation, preservation, and safe abort. 02 · Why this problem matters

Recovery is easy only when the world is reversible.

A local checkpoint can restore an agent’s execution state without undoing the email it already sent, the record it already changed, or the shared artifact another actor edited while the agent was recovering.

The problem

Computer-use agents act across mixed state domains: local UI state, application state, shared state, and committed external effects.

Why it is hard

The same failure signal can mean “nothing happened,” “it committed,” “it committed to the wrong target,” or “the world changed concurrently.”

Why generic recovery fails

Blind retry can duplicate effects. Rewind can restore the agent while leaving the external world unchanged. Aggressive compensation can erase valid work by another actor.

03 · Core idea

A failed tool result does not tell you whether to retry. The realized world state does.

Resutura treats recovery as effect-state reconciliation. It separates rewindable local state from committed external state, records actor ownership and tool guarantees, then selects the smallest safe recovery semantics supported by observable evidence.

Novelty boundary: Resutura does not claim to invent rollback, compensation, idempotency, causal repair, or verify-before-retry. The research hypothesis is the integration of recovery choice across heterogeneous realized effect classes and tool contracts in computer-use workflows.

04 · Architecture

Policy proposes. Resutura verifies the world.

The action policy and recovery runtime are deliberately separated. The policy proposes the next action plus expected postconditions; the recovery runtime owns state verification and recovery semantics.

08 · Failure analysis

What failed, why, and how recovery changed.

01

Wrong-target committed effect

The agent intends research-team, but the publication commits to wrong-channel. Rewind cannot erase the external effect. Resutura identifies the agent-owned ledger entry, retracts it, publishes once to the intended target, and re-verifies protected progress. Measured recovery overhead: 2 actions.

02

Acknowledgement lost after commit

The write commits, but the caller sees a timeout. Blind retry duplicates the intended effect; Resutura and the Verification-Aware baseline use authoritative readback and continue without replay. This is deliberately retained as a case where Resutura does not uniquely win.

03

Concurrent valid state + agent misdirection

Another actor publishes a valid coordinator note before the agent's own publication is misdirected. Ownership-aware compensation repairs only the agent-owned damage and preserves the external update. Removing effect ownership drops task success to 0% in the formal ablation.

04

Non-compensatable committed effect

No safe inverse exists. Resutura returns R7_safe_abort, preserves recoverable prior progress, and refuses to relabel the task as successful.

11 · Safety / limitations

Some failures should not be “recovered.”

Irreversible actions

If no safe compensator exists, Resutura safe-aborts. It does not relabel an impossible reversal as task success.

Permission boundaries

Real deployments need authorization checks before compensation, rollback, deletion, or cross-account changes.

Human escalation

High-impact or ambiguous state transitions should escalate when evidence is insufficient to choose a safe recovery semantics.

Current limitation

No frontier-model, OSWorld, production security, or SOTA claim. Chromium evidence uses a deterministic planner.

Tool-contract dependence

Readback and idempotency can eliminate the need for sophisticated runtime recovery in some failure classes.

Threat model

The current suite focuses on accidental divergence and state semantics, not malicious tool servers, prompt injection, or compromised credentials.
